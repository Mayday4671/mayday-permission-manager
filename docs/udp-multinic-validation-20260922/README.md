## 本次交付

## 随机负载验收

用户确认负载为 100–1472 字节、200 Mbps。测试采用固定哈希生成近似均匀的变长包，覆盖该区间；按累计实际字节定速，序号在第 9–16 字节，逐包检查长度及其余所有字节，仅允许第 3–4 字节变为 03 01。多网卡时两个源合计 200 Mbps（额外测试合计 220 Mbps），不是每源 200 Mbps。

最终代码的 **18 轮测试，共 26,233,422 个唯一数据包**，缺失、重复、内容错误均为零；多网卡接收端逐包核对发送源 IP/端口，错误为零。所有 Linux 监听 socket 的内核丢包为零；Windows 无此系统计数，依靠源端与接收端序号核对，没有把“未知”写成零。

1. 三网卡五轮 30 秒：两张网卡分别接收不同上游，第三张网卡绑定源地址发往独立接收端；NIO/EPOLL 覆盖 200 和 220 Mbps。
2. 三网卡 5 分钟：EPOLL、200 Mbps、100–1472 字节随机包，共 9,542,566 包、7,499,998,085 字节，收包/转发/唯一接收完全一致，接收端速率约 200.087 Mbps。
3. 独立模块九轮全新 JVM：Windows/NIO、Linux/NIO、Linux/EPOLL 各三轮 30 秒，200/220 Mbps。每轮从首包计数，无流量预热。
4. 已部署 Java 后端三轮完整重启：通过真实权限接口启动，每轮 30 秒、953,714 包，逐秒读取页面使用的统计接口，最后只停止自身批次。三轮均无缺包。

端点总速率允许 0.5% 的调度/计时误差；丢包、重复、内容错误容差为零。单秒统计受采样边界影响，不能用某个瞬时峰值代替整轮速率。完整逐轮结果见 [results.json](results.json)。

## 未通过的边界

100 字节集中发送、200 Mbps 相当于 250,000 PPS。在相同三网卡虚拟环境中，10 秒发送 2,500,000 包，只收到/转发/唯一接收 559,251 包，内核丢包 1,940,749；应用丢弃与发送失败为零。这轮**失败**，不能用随机测试成功覆盖它。

早期 523 字节集中发送在 210/250 Mbps 下也出现内核积压，原始失败全部保留。性能采样主要落在系统发送调用；这说明当前实现与部署组合存在 PPS 边界，不能仅靠放大缓冲声称解决持续过载。近似均匀随机包在 200 Mbps 下约 32,000 PPS，与最小包集中的压力不同。

要判定实际业务的不丢包指标，仍需在真实转发服务器上使用真实包长分布及峰值 PPS，检查物理网卡、路由、交换链路和接收端。普通 UDP 没有接收确认/重传，仅修改现有报文的第 3–4 字节无法补回链路或对端丢包；本次不擅自更改业务协议。

## 部署与系统设置

本次将 Docker Desktop Linux 虚拟机的 net.core.rmem_max 和 net.core.wmem_max 从 212,992 提高到 16,777,216 字节。没有修改防火墙、路由、rp_filter，也没有增加容器特权。设置为虚拟机级临时值，Docker 虚拟机重启后须复查，缓冲未获授予时新版本拒绝开流。V16 小缓冲冷启动失败保留在 [历史记录](../udp-relay-validation-20260922/README.md)。

三网卡试验使用三个独立 Docker internal 网络、两个上游容器、一个下游容器，流量不发往外部设备；测试网络和容器均在结束后清理。页面只能列出当前 Java 进程可见的接口，容器网卡不是宿主物理网卡；物理机部署建议直接运行 JAR 并核对系统路由。

## 复测入口

独立模块先构建 test-classes 与运行依赖，再依次执行 scripts/verify-udp-matrix.mjs、scripts/verify-udp-multinic.mjs；它们不可并行打流，以免互相争用机器。已部署后台复测使用 scripts/verify-udp-relay.mjs，仅接受停止状态和默认本机目标，不覆盖其他人的运行批次。

脚本默认包含随机包、200/220 Mbps、不同平台以及三网卡 5 分钟测试。边界条件可通过多网卡脚本的 UDP_NIC_CASES 参数复现，例如 [[7,"EPOLL",100,200,100,10]]；其字段依次为轮次、模式、最大包长、合计 Mbps、最小包长、持续秒数。任何失败返回非零状态并保留证据。
