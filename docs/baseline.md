# P0 开发基线与验证方法

本文保留 P0 阶段记录。当前版本已于 2026-09-19 完成 P0–P6 交付与本机升级；最新结果见 [P6 完整验收](p6-validation/README.md)。

## 环境与验证范围

日常环境使用 `compose.yaml`，项目名为 `mayday`。P0 开始时，该环境数据库已执行 V1、V2；工作目录还存在未应用的 V3 及未接入页面的模块代码。

验证环境使用 `compose.verify.yaml`。脚本每次生成独立的 `mayday-check-时间-随机值` 项目，分别建立升级库与空库。验证后端默认占用本机 18081、18082，数据库不映射宿主机端口。

日常服务和验证服务互相独立。验证脚本只读取日常数据库；所有测试写入、升级及恢复发生在本次创建的验证环境中。

## 运行方式

前提：Docker 已运行，当前日常 MySQL 可连接，`.env` 中的管理员密码与实际账号一致，已安装 Node.js 24 和 Java 21。

在项目根目录运行：

```powershell
# 类型检查、构建及工作区标签页测试
npm --prefix frontend run build
node --test tests/workspace.test.mjs

# 后端构建与单元测试；也可由下面的 Docker 验证构建执行
$env:JAVA_HOME='D:\Soft\JDK21'
Push-Location backend
.\mvnw.cmd -B verify
Pop-Location

# 完整的备份、恢复、升级、空库安装、接口回归及重启验证
node scripts/verify-baseline.mjs
```

如果验证端口已被其他程序使用，可通过 `VERIFY_UPGRADE_PORT`、`VERIFY_FRESH_PORT` 指定其他本机端口。脚本不会关闭占用端口的其他程序。

每次结果位于 `.local/baseline/<runId>/`：

- `source.sql`：单事务 SQL 备份，包含业务数据及迁移历史，二进制字段使用十六进制编码。
- `result.json`：每项验证结果、备份摘要及清理结果。
- `source-migrations.txt`、`upgrade-migrations.txt`、`fresh-migrations.txt`：迁移版本及校验和。
- `api-upgrade.log`、`api-fresh.log`：真实 HTTP 与 MySQL 回归结果。
- 构建、容器启动、重启、容器运行和清理日志。

备份含本机业务数据，保存在已被 `.gitignore` 排除的 `.local` 中，不写入公开文档或代码仓库。测试完毕清理的是本次临时容器和数据卷，备份与验收日志保留。

## 保留数据升级如何验收

1. 读取源库迁移版本，为原账号、角色、授权关系、数据范围、组织/配置与内容生成字段摘要。
2. 使用单事务备份，并在独立升级库恢复，先核对恢复结果。
3. 同一个后端构建分别对升级库和空库启动，校验两者迁移版本、校验和及成功状态一致。
4. 升级后比较原业务字段；新增结构和分类记录允许存在，原角色权限不允许被迁移追加。
5. 在两种数据库上运行接口回归，覆盖数据范围、越权、敏感字段、发布、回收站、版本冲突、撤权、会话与审计。
6. 清理测试创建的明确 ID，确认原记录不变，然后重启升级后端，验证没有重复初始化。
7. 再次核对日常源库的迁移与业务摘要；保存结果并销毁临时环境。

验证期间若日常环境恰好有人修改了上述业务数据，摘要比较会失败；应确认修改来源后重新验证，脚本不会覆盖这些修改。

已执行的 V1、V2 不作改写。P0 修正 V3 前已经确认日常库未执行该版本；后续一旦 V3 应用，修正通过新增迁移实现。

## 本批修复

- 通知详情在没有选中记录时不再把空值传给日期格式化函数，前端恢复可构建状态。
- 新模块迁移不向已有角色自动增加通知/审批权限，不提前生成尚未接入的页面菜单。
- 普通角色初始化只使用明确的权限列表，避免引入未声明的默认权限。
- 关键词查询统一到 `SearchPredicates`，显式声明 SQL 转义字符；百分号、下划线、感叹号和反斜杠按文字检索。
- 公开内容列表与详情显式排除回收站内容。
- 回归清理适配软删除：先软删除并彻底清理测试内容，再清理用户、角色和部门；失败会汇总报告。
- MySQL 验证环境通过 TCP 和业务账号执行查询检查就绪，避免把初始化期间的临时服务误判为已启动。

## 后续模块接入契约

- **权限名称**：继续使用 `resource:action`；定义在 `PermissionCatalog`，接口负责授权，菜单显示不是授权依据。增加新权限不等于给已有角色自动授予。
- **角色名称**：中文显示名称允许修改，不用于权限判断；受保护的管理员角色编码使用 `admin`。业务页面只判断具体权限。
- **列表协议**：`items/total/page/size`，页码从 1 开始，单页 1–100 条。用户关键词通过 `SearchPredicates.contains` 构造字面量查询。
- **响应协议**：保留 `success/data/message`；400 参数或业务条件错误、401 未认证、403 越权、404 不可访问的公开内容、409 版本或唯一性冲突、429 登录限流、500 内部异常。
- **版本检查**：修改请求携带读取时的 `version`。遇到 409 保留用户输入并提示刷新，不自动覆盖新版本。
- **路由登记**：页面完成、接口授权与测试就绪后，才登记路由、菜单及页签。当前涉及 `App.tsx`、`workspace-model.ts` 和服务端导航；P1 将前端页面元数据合并为单一登记来源。
- **模块状态**：目前通知/文件/会话/网站配置存在部分页面源码，顺序审批存在部分接口；未接入并验收前，不按已交付功能宣传。
- **迁移**：新版本追加文件，已有授权不自动扩大，旧业务记录不覆盖。空库安装与保留数据升级都需要验证。
- **注释**：公共接口、权限规则、状态流转、并发处理及异常边界说明原因和使用约束；不靠重复字段名的注释充数。

## 恢复与回退原则

本批已通过把备份导入独立环境验证恢复能力。实际升级前保留对应的 SQL 备份和前后端版本；需要回退时先停止业务写入，在新实例中恢复迁移前备份，启动与该备份兼容的旧版本，通过登录、权限和内容检查后再切换。

不要让旧后端直接操作无法保证兼容的新结构，也不要用删除日常数据卷作为回退方式。应用日志、备份和迁移状态应随版本一起记录。
