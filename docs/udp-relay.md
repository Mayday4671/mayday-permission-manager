# UDP 转发

入口：左侧独立的 **UDP 转发** 菜单，位于工作台下方。配置、启动、停止由页面操作，实时显示接收/转发包数、待发送数、本机已知丢包、收发 Mbps、每秒包数与最近 60 次速率采样。配置与运行统计独立；刷新或关闭页面不会停止正在运行的转发。

## 使用

1. 点击“配置”，填写接收 IP、接收端口、单个目标 IP 和目标端口。接收 IP 指运行 Java 服务的机器；`0.0.0.0` 表示全部 IPv4 网卡。目标必须为单播 IP，不接受域名或指向本机同一接收端口。
2. 多网卡时选择发送源 IP，可指定发送源端口（0 表示系统分配）；下拉列表来自 Java 服务所在机器的实际网卡。传输模式默认 AUTO，Linux 优先 EPOLL，也可固定 NIO 或 EPOLL 排查平台差异。
3. 默认申请接收、发送缓冲各 16 MiB，应用待发送内存上限 64 MiB。实际缓冲小于申请值时拒绝启动，先修正系统限制再开流。
4. 先启动目标接收程序，再点击“启动转发”，最后启动上游打流。默认负载至少 8 字节，第 3、4 字节改为 `03 01`，其他字节不变。
5. 停流先停止上游，等待待发送数归零后再停止转发。运行中不能改配置；每次启动重新计数，停止保留本次统计，应用重启默认停止。

计数定义和可移植接入方式见 [独立模块说明](../backend/mayday-netty/README.md)。发送失败、待发送内存超限、不足 8 字节与系统接收丢包分别列出；系统值不可读时显示“不可用”。本机发送成功不等于对端收到，验收必须同时核对端点序号。

## 部署

本机 Docker 默认只向宿主 `127.0.0.1:19000/udp` 映射接收端口。`compose.yaml` 的 `UDP_LISTEN_PORT` 必须与页面接收端口一致；修改页面端口不能自动修改 Docker 端口映射。局域网发流时，将 `.env` 的 `UDP_BIND_ADDRESS` 改为宿主指定网卡 IP，并按部署环境放行该 UDP 端口。转发到宿主机上的接收器时，目标填写容器可达的宿主网关 IP，不是容器内的 `127.0.0.1`。

Linux 物理网卡持续打流建议直接运行后端 JAR，或按实际环境配置宿主网络。这样页面选择的本地网卡与端口直接对应服务器。此模块为单 JVM 单路监听，不设计成集群调度器；多副本应固定一台转发实例与管理请求入口。

### 接收缓冲受限

必须核对页面“实际接收 / 发送缓冲”，不能只看配置申请值。V16 的 Docker Desktop 系统上限为 212,992 字节；Linux 原生接口返回加倍后的 425,984 字节，曾发生冷启动内核丢包。V17 统一 NIO/EPOLL 的显示口径，扣除 Linux 返回值中的加倍管理开销，并在开启接收前校验实际缓冲；不足时明确报错并释放端口，不能继续启动。

Linux 部署由运维根据机器资源设置 `net.core.rmem_max` 与 `net.core.wmem_max`，至少允许所需的 16 MiB socket 申请，再停止并重新启动转发使新值生效。参考 [Linux 内核 socket 缓冲说明](https://kernel.org/doc/html/latest/admin-guide/sysctl/net.html)。Linux 返回值可能包含加倍的内核管理开销，不等同于能保存同等大小的 UDP 负载。

某些 Docker Desktop 内核不提供容器级这两个 sysctl，直接添加 Compose `sysctls` 会导致容器启动失败。本次在 Docker Desktop 的 Linux 虚拟机中将这两个上限从 212,992 提高到 16,777,216 字节；没有改变防火墙、路由或反向路径检查，也没有给后端增加特权。该修改只影响允许申请的 socket 缓冲上限，不预先分配全部内存。

Windows Docker Desktop 的本机设置命令为 `wsl -d docker-desktop -u root -- sysctl -w net.core.rmem_max=16777216 net.core.wmem_max=16777216`。这是虚拟机级临时设置，Docker 虚拟机重启后可能恢复，届时须重新检查并设置；程序不会自动提权修改内核参数。实际 Linux 服务器应由部署人员将相应配置写入系统 sysctl 配置并核对生效值。

正式网络验收需要同时记录网卡丢包、系统丢包和接收端序号；单纯增大应用待发送内存不能挽回进入程序前已经丢失的包。

### 多网卡收发

- 接收 socket 只做 bind，不做 connect，不绑定某个上游 IP/源端口；不同网卡、不同上游可同时向监听地址发送。使用具体接收 IP 仅监听该本地地址，`0.0.0.0` 监听全部 IPv4 地址。
- 发送使用独立 socket，绑定所选源 IP/端口，再连接单个目标。页面显示实际监听地址、实际发送源及最近发包源，便于与抓包结果比对。发送源端口独立于接收端口，本模块不做回包代理。
- 指定源 IP 不等同于 `SO_BINDTODEVICE`；最终出接口仍由操作系统路由决定。三张网卡在不同子网时应有对应直连路由；同子网多网卡、非对称路径或经网关转发，需要在目标服务器核对路由/策略路由与反向路径检查，不能仅凭 Java 配置保证走某一块物理网卡。
- Windows 使用 NIO；Linux 可分别使用 NIO 与 EPOLL 验证。强制 EPOLL 在不支持的平台明确拒绝启动。没有增加端口复用、流量整形或复杂业务处理到收包路径。

## 模块与权限

- `backend/mayday-netty`：独立普通 Java 核心与打流验收工具，不依赖 Spring/MySQL/Mayday。
- `backend/mayday-application/.../relay`：持久配置、权限、串行启停和 HTTP 适配，不进入逐包路径。
- `relay:view`：读取配置和统计；`relay:configure`：修改配置；`relay:control`：启停。后两项同时要求查看权限。普通角色默认不获得这些权限。
- 运行中的系统服务不依赖启动人的浏览器会话。撤销权限立即禁止其后续管理请求，但不会擅自中断已经启动的转发；由仍获授权的运维账号停止。
- V16 新增 `udp_relay_config` 和菜单，V17 增加发送源 IP/端口和传输模式。唯一交付 SQL 为 `database/mayday.sql`；40 张业务表、373 个业务字段均有中文注释，不保存任何逐包正文或统计日志。

## HTTP 接口

所有接口要求有效后台会话，统一返回 `ApiResponse`：

- `GET /api/relay/config`：读取持久配置及 `version`。
- `GET /api/relay/interfaces`：读取网卡名称、地址、前缀长度、MTU、启用/回环状态，要求 `relay:view`。
- `PUT /api/relay/config`：提交 `bindIp`、`bindPort`、`targetIp`、`targetPort`、`receiveBufferMiB`、`sendBufferMiB`、`pendingMemoryMiB`、`sendIp`、`sendPort`、`transportMode`、`version`。必须停止后修改；旧版本返回冲突。兼容 V16 请求，缺省新字段分别为空字符串、0、AUTO。
- `GET /api/relay/stats`：读取每秒更新的不可变快照。速率不由浏览器估算。
- `POST /api/relay/start`：`{"version":0}`，启动当前配置并创建新 `runId`。
- `POST /api/relay/stop`：`{"runId":"当前批次"}`，拒绝过期页面误停新批次。

没有公开网络打流接口，没有自动启动监听，没有隐藏按钮代替后端鉴权。
