# 安装、升级与恢复

## 空库安装

复制 `.env.example` 为 `.env`，设置数据库及首次管理员密码，再执行 `docker compose up -d --build`。Flyway 顺序应用 V1–V22，Hibernate 只校验结构。默认 `SEED_DEMO_DATA=false`，只建管理员与必要基础资料；设 true 仅供首次体验演示。初始化幂等，重启不覆盖既有账号、密码和普通角色授权。默认服务仅绑定 127.0.0.1，后台/门户端口 15173，接口 18080，MySQL 13306；UDP 19000 只建立端口映射，转发须在页面手动启动。

V12 只补充 35 张表和 301 个字段的中文 COMMENT。MySQL DDL 会隐式提交；脚本失败时保留现场并核对已完成的语句，不能假设数据库自动回滚所有 DDL。原 V1–V11 校验和不修改。

V13 新增采集任务及队列表；V14 新增文章、正文与配图引用。V15 新增配置归档标记，拆分“采集数据”和“采集配置”菜单；仅把默认菜单名“图片采集”改为“采集数据”，保留自定义名称及原授权。V16 增加 UDP 转发配置表及菜单，默认不启动监听，不向普通角色授予转发管理权限。V17 增加发送源 IP、发送源端口和传输模式，默认值兼容原配置；新版本启动前要求操作系统实际授予配置中的收发缓冲大小，部署时先检查系统上限，见 [UDP 部署说明](udp-relay.md)。当前完整初始化脚本为 51 张业务表、506 个字段。删除有文章的配置只归档，数据继续保留；不要回退到不识别归档标记的 V14 应用，以免重新显示或执行已删除配置。旧任务需要复制重跑才能采集此前未存储的正文。不自动删除新表或已采集文件。

V18 增加工单扩展示例，V19 增加文件存储、目录/回收站、批量任务、反馈、监控策略、审批催办和变更审计；V20 增加 OA 草稿、退回重办与提交轮次。V21 新增门户栏目、分类归属、首页编排三张表及修订栏目外键；只补齐旧分类归属，不改原文章正文、发布指针、审批历史或普通角色授权。完整索引/外键口径为 128/48，不计 Flyway 历史表。已用过的迁移保持原校验和。

V22 仅更新会话创建、活动和到期三个字段的中文 COMMENT，使数据库注释与可配置会话策略一致；不修改字段类型、值、索引或授权。单一安装脚本同步到 V22，下一新增迁移从 V23 开始。

## 保留数据升级

1. 保持当前 MySQL 运行，完成 `node scripts/verify-baseline.mjs`。它备份并在独立 MySQL 恢复，分别验证升级与空库；成功结果与 SQL 备份位于 `.local/baseline/<runId>/`。
2. 执行 `node scripts/upgrade-local.mjs`。脚本要求日常迁移版本与最近通过验收时的源版本一致，并校验源码、配置模板及验收脚本的内容摘要，包含未提交的新文件。缺少摘要的历史记录或验收后变化的代码不能直接升级。先构建新镜像、再次核对输入未变化，并为旧镜像加保留标签。
3. 脚本停止前后端业务写入，保留 MySQL 及命名数据卷，同时备份完整 SQL 和 LOCAL 文件正文，再启动新版本。核对迁移校验和、原账号/角色权限/组织/内容字段及服务健康状态。
4. 打开登录、工作台、系统管理、通知、审批与门户检查。授权新模块请使用明确权限；升级不会给普通角色自动扩权。

升级期间不要运行其他直接写入同一数据库的开发服务。`.local` 的 SQL、日志及快照可能含真实数据，只在受控位置保留，不提交到公开仓库。

## 备份内容和位置

`.local/upgrades/<时间>/result.json` 保存升级结果、验证来源、构建输入摘要、SQL SHA-256 和旧镜像标签；同目录 `before.sql` 是停写后的完整库，`before.json` 是核心业务字段摘要。`files/` 是同一停写恢复点的 LOCAL 正文，`files-manifest.json` 为每个相对路径记录长度与 SHA-256。构建、启动及查询记录只保存在该目录。

旧 MYSQL 文件随 SQL 保存，S3/MinIO 对象不包含在 LOCAL 目录备份中，需另行执行对象存储备份。空本地目录也是明确的备份结果，不能因此假定外部存储已备份。真实 `.env` 不写入源码摘要或公开验收报告，应由部署方受控保管。

## 故障处理与回退

构建失败发生在停止现有服务之前，不影响当前运行。备份/迁移/启动失败会停止脚本并保留所有文件和卷；先查看 result.json 与对应日志。不要删除 mysql_data，不要改写 flyway_schema_history 或已执行迁移来“修好”校验。

旧应用不能假定兼容新数据库。回退时先停止业务服务，核对 backup 的 SHA-256，在新建的独立 MySQL 环境恢复 before.sql，使用 result.json 记录的旧前后端镜像连接恢复库，验证账号、授权和文章后再切换入口。保留出问题的新库供排查；不要直接覆盖唯一一份日常数据。恢复步骤由实际数据库路径、目标库和数据保留要求决定，不能用通用删库命令代替。

恢复文件时还需将同一记录的 `files/` 放入隔离目标的持久卷，核对 `files-manifest.json` 完全匹配，并给予应用 `mayday:mayday` 读取权限。数据库引用、正文和目录信息必须来自同一恢复点。先验证正常鉴权下载、逐文件字节一致及缩略图，再切换入口；不能用另一时刻的文件副本拼接数据库备份。

文件回归在随机隔离项目内真实移除测试正文、确认无法下载，再从完整目录备份恢复并逐字节核对；不触碰日常文件。最近验收结果见 [企业交付检查](enterprise-validation-20261004/README.md)。未进行跨地区容灾或生产负载认证。生产配置、探针、会话与分离数据库账号步骤见 [生产指南](production.md)。

## 时间与配置

内容排期采用 Asia/Shanghai，本机与容器使用同一时区；API 返回无偏移本地时间，前端明确标注北京时间。`.env` 的 ADMIN_PASSWORD 只初始化空库账号，不能用于重置已有密码。网站公共配置通过配置服务及白名单发布；刷新配置不修改系统凭证。
