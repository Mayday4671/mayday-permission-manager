# 工作台待办与站内消息

本次补齐工作台入口，已有审批引擎与可靠通知事件继续复用，数据库结构未改变。

## 用户使用方式

- 审批流转到当前用户时，在工作台「待办审批」显示数量和最近三条，点击记录可直接在弹窗处理。「全部」进入审批待办列表。
- 工作台「未读消息」显示个人通知，右上角铃铛显示未读总数；点击消息打开详情，成功读取并重新鉴权后标记已读。审批消息可打开关联申请。
- 消息已读与审批处理独立：读通知不会消除待办，仍须同意、驳回、转交等有效操作；申请结束后结果通知申请人。
- 站内事件通常由每 3 秒执行的投递任务送达；可见页面每 15 秒查询一次，返回页面也会重新查询。处理/阅读后立即刷新相关数据。未实现 WebSocket 或浏览器系统推送。
- 待办区需要 requests:view + requests:approve，消息区需要 messages:view；工作台页面仍需要 dashboard:view。权限由现有角色配置，页面不会替用户扩大授权。

## 实现

- PersonalWorkPanel 替换首页原快捷入口区域，避免额外堆叠整行卡片；原有用户、角色、组织和内容入口仍通过指标卡及侧栏访问。无待办/消息权限的账号继续保留原快捷入口。
- personal-work.ts 统一个人查询和刷新周期，缓存按账号区分。数量使用服务端 total，列表只取前三条；前端不做全量数据的权限筛选。
- ApprovalDetailModal 与 MessageDetailModal 供页面复用；消息正文关闭后释放缓存，阅读失败不虚报成功并提供重试。错误状态不展示旧记录，加载/空态不使用占位插画。
- 保留单侧折叠菜单、页签、弹窗以及前后台独立主题；未改动数据库脚本或后端业务规则。

## 验证范围

- 新增真实 MySQL 回归：A → B 审批，后续节点不提前生成待办、无关用户不可访问消息或处理任务、阅读不清除待办、处理后流转、结果通知申请人。
- 原有或签、会签、转交、加签、撤回、事务通知失败重试和唯一投递检查继续运行。
- 浏览器主要验证本机现有账号的首页、页签、列表入口、空态和桌面/窄屏布局；审批多账号流转通过隔离数据库 HTTP 回归验证，不在日常数据库创建临时审批业务记录。
