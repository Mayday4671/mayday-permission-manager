# 权限设计与约束

图片采集使用独立的 `crawler:view/create/update/delete/run/stop/download/all` 权限。默认按任务创建者隔离，`all` 授予管理他人任务能力；运行同时需要 `files:create`。工作器每次领取与入库前从数据库重新校验执行人的有效账号、角色和权限。下载核对结果项所属任务，文件中心引用检查包含采集结果。详见 [图片采集](image-crawler.md)。

## 三层授权

1. **页面入口**：`/api/system/navigation` 根据启用菜单及当前权限返回可见导航；直接输入 URL 仍有前端 Guard。
2. **接口操作**：后端 `@PreAuthorize` / `AccessPolicy.require()` 独立检查 `resource:action`。隐藏菜单不代表撤销接口权限。
3. **记录范围**：列表查询在 SQL 条件中加入范围；修改、删除再次检查记录作者或所属部门。

权限目录唯一来源为 `PermissionCatalog`。未知权限不能写入角色。授予操作时必须同时授予同资源的查看权限。

`scoped=true` 的资源统一生成后端范围白名单、角色范围编辑表单和会话摘要；新增业务仍必须在列表、单条、导出/统计及异步任务上实际调用授权策略。所有接口默认要求认证，但认证本身不是资源授权，不能省去新接口的动作检查。

## 操作粒度

所有常规资源分别有 `view/create/update/delete`。此外：

- `users:assign`：调整用户角色，且只能授予自己可委托的角色。
- `users:reset`：重置他人密码，与资料编辑完全分离。
- `users:export`：导出授权范围内记录，不自动包含敏感字段。
- `users:sensitive`：查看和维护邮箱、电话。无权时响应字段为 null，输入同名字段也不能覆盖原值。
- `users:email-read/email-write`、`users:phone-read/phone-write`：邮箱、电话分别设置读写权限。写权限必须同时有对应读权限；旧 `users:sensitive` 保持兼容。列表、导出和修改同样执行字段限制；普通资料编辑回传隐藏字段的 null 时保留原值。
- `roles:grant`：角色新增和修改权限集合时，同时需要 create/update。
- `notices:publish`：发布、下线和删除正在展示的内容。编辑权可以生成新草稿，但不会覆盖线上修订。
- `logs:view/export/delete`、`loginlogs:view/export/delete`：两类日志分别授权查看、导出与清理。清理至少保留最近 30 天；不能通过详情 ID 或修改分类参数绕过另一类日志的授权。
- 工作台的“最近操作”和操作趋势只包含操作日志，即使持有 `logs:view` 也不会带出登录日志。
- `sessions:view/revoke`：查看与强制下线分离。本人会话可自助管理；其他账号的会话须具备 `users:view` 并落在当前用户数据范围。撤销他人会话还检查目标角色的管理边界，不能强制下线权限更高的账号。搜索、总数和分页均先按范围过滤。
- `userstats:view`：还需 `users:view`，账号数量和成功登录人数沿用用户范围。失败登录不能可靠归属部门，仅全部用户范围且有登录日志查看权时返回全局失败次数。
- `scheduler:view/create/update/delete/execute`：受控内部任务的独立权限；数据库检查只返回连接正常，不返回全站用户数量，调度权不能代替用户查看权。
- `relay:view/configure/control`：单路 UDP 服务分别授权查看（包含本机网卡清单）、配置和启停，配置/启停同时要求查看权。配置只能在停止后按版本修改，停止必须匹配当前批次，防止旧页面误停新服务。所有角色默认不增加此权限，运行服务不跟随操作人的浏览器退出而停止。详见 [UDP 转发](udp-relay.md)。

## 数据范围

用户与内容分别配置，不把一个模块的范围误用于另一个模块。

- `SELF`：用户自身记录；内容的作者为当前用户。
- `DEPARTMENT`：本人加当前部门记录，不包括下级部门。
- `DEPARTMENT_TREE`：本人加本部门及所有下级部门记录。
- `CUSTOM`：精确指定的部门集合，不自动含本人或下级部门。每个资源独立保存部门 ID。
- `ALL`：全部记录。

多个启用角色按可访问记录取并集，例如“本人 + 指定 A 部门”可以看到本人及 A 部门，不会扩大到本人整个部门。**只有具备当前资源查看权限的角色参与该资源范围合并**。有查看权但未配置范围时默认为本人，无部门用户不会自动看到未分配部门的其他人。会话中的 `dataScopes` 是展示摘要，服务端最终查询按实际角色集合计算，不用摘要代替 SQL 范围。

不支持显式拒绝规则或任意行字段表达式。部门树结构写操作只允许超级管理员，因为移动部门会改变整个数据授权范围。被自定义数据范围引用的部门不能删除。

## 防止授权升级

- 内置 `admin` 角色不可修改或删除，初始 admin 用户不能删除、停用或丢失管理员角色。
- 用户不能在管理接口中修改自己的角色或停用自己；通过个人中心维护基本资料。
- 非超级管理员不能授予自身没有的操作权限，也不能管理权限更高的账号或角色。
- 部门范围与受让人部门有关，直接比较范围等级不能保证委托安全。因此当前版本只有超级管理员可跨人员委托部门/全部范围；普通权限管理员只能委托 SELF 范围。
- 创建用户要求 ALL 用户数据范围；改变所属部门仅允许超级管理员。
- 已被用户引用的角色不能删除；存在下级或成员的部门不能删除。
- 已被账号关联的岗位不能删除；部门负责人账号删除前必须调整负责人。
- 批量启停只接受 ID、版本和目标状态；每条记录执行与单条编辑相同的范围、角色等级及内置账号保护。任一记录失败则事务整批回滚。

## 会话与审计

登录签发 256 位随机 Bearer 令牌，12 小时到期；数据库只存 SHA-256 摘要。前端放在当前标签页 sessionStorage，不写入 URL 或持久 localStorage。每个请求重新读取账号状态和角色授权，不把过期权限缓存在令牌中。

退出登录撤销当前令牌，修改/重置密码和停用账号撤销该用户所有令牌。BCrypt cost 为 12，密码至少 10 个字符并包含字母、数字；BCrypt 输入最多 72 个 UTF-8 字节。

登录失败按来源 + 用户名限制 5 次 / 15 分钟，来源汇总限制 100 次 / 15 分钟。成功登录不会消耗失败额度。当前为进程内限流，多节点需替换为 Redis 等共享实现；代理部署需结合可信代理规则配置真实来源地址。

登录前必须完成服务端拼图验证：随机题目答案不下发，每题仅一次尝试；通过凭证绑定账号和来源、60 秒内只能消费一次，密码错误也作废凭证。获取题目另有来源限流和内存容量上限。挑战及凭证当前存于单实例内存，多节点须用共享存储原子消费；拼图属于基础反自动化门槛，可被图像算法识别，不能替代密码限流、MFA 或专业风控。过期、重放、错误位置、绑定和并发消费分别有单元及真实 HTTP 验证。

写操作及导出记录到审计表，失败同样记录。审计记录操作人、路径、HTTP 方法、状态、IP 和耗时；不存储正文、查询参数、原始令牌或密码。登录成功记录真实账号；失败登录中的用户名是请求者声明的登录账号，不能解释为该账号的已认证行为，必须结合失败状态判断。

## 并发与一致性

所有编辑请求携带 `version`。客户端版本过期时返回 HTTP 409，提示刷新，避免后提交覆盖先提交。业务写入使用数据库事务，角色编码/用户名有唯一约束。删除、修改部门时检查引用及父链循环。

这些限制由 `tests/api.test.mjs`、`tests/workflow.test.mjs`、`tests/security.test.mjs`、`tests/theme.test.mjs` 和 `tests/captcha.test.mjs` 在真实 MySQL 上验证；`scripts/verify-baseline.mjs` 对空库和升级库均执行回归，并验证注释及纯净初始化。增加新业务时，必须为列表、详情、更新、删除、导出和摘要聚合入口同时应用授权策略；仅保护列表是不完整的。

## 通知、文件和审批

- `notifications:view/create/update/delete/publish/withdraw/all` 分离；没有 `all` 只能管理自己创建的通知。选取接收人也按用户数据范围检查，发布时再次校验并冻结接收者。
- `messages:view` 只允许读取当前用户自己的投递；通知管理权不能替代收件权限。附件入口再次检查接收权、撤回和过期。
- `files:view/create/download/delete/all` 分离。上传者或全量文件管理员可关联文件；被通知、内容修订或审批引用的文件不能删除。公开文章附件、审批字段附件和文件中心采用各自的业务鉴权入口。
- `approvalcategories:*` 管理流程分类，已引用分类受保护；`workflows:view/create/update/delete/publish` 管理模型，发布是单独权限。已发布/已引用流程不能删除，可以停用。
- 流程模型人员名称回显沿用用户查看权限与数据范围。模拟还需 `users:view`；指定人员、角色、部门负责人三种来源解析出的每一位审批人都必须在范围内，否则整次模拟返回 403，不能通过模拟模型建立全局人员查询入口。已发布流程的实际运行仍使用冻结的业务授权，不因申请人的通讯录范围截断审批链。
- `requests:view/create/approve/manage` 分离；查看还需要本人发起、已实际参与的节点或 `manage`。未来节点人员不能提前查看；管理员的全量查看权不能代替待办处理权。
- 处理同时检查当前待办人、账号启用、当前审批权限、节点动作、字段可写范围与版本。自审和重复审批默认禁止；无有效审批人直接阻止提交/流转，不自动通过。
- 字段可读作用于详情、附件和字段变更历史；可写必须是可读字段子集。原始提交数据独立保存，审批人的调整记录修改前后值。转交后原任务不能继续处理；加签为必签，不能代替或签节点原审批人的决定。
- 内容审批需 `requests:create` 和该文章的 `notices:update` 及数据范围。审核人通过申请查看送审快照，不因此获得整个内容中心权限。审核通过只批准绑定修订，实际发布仍需 `notices:publish`。
- `requests:manage` 可以查看投递事件及安排重试；业务事件与审批同事务提交，通知失败不会伪造审批结果，重试不重复投递。

前端在窗口重新聚焦及可见状态每 30 秒刷新会话权限，并清理失去访问权的菜单/页签。服务端在每次请求立即重新鉴权，前端刷新间隔不会延迟接口撤权。
